# Using MemLens

Part of the MemLens documentation; start with the [README](../README.md).

## Usage

In IDA, with any database open (plugin menu entries need one), under **Edit > Plugins**:

1. **MemLens: Export kernel from memory image**: choose the image. `kernel.elf` is written next to it (`kernel-1.elf` if one is already there; the message names the file). MemLens asks for the ISF and hands it to Volatility (Cancel uses Volatility's own symbols path, which has no Linux ISFs after a plain pip install). If Volatility finds no kernel, the error dialog says which kernel the image holds, or that it holds none (see [When the export fails](EXPORT.md#when-the-export-fails)).
2. Open `kernel.elf` in IDA.
3. **MemLens: Apply kernel types from ISF**: choose the ISF. If its kernel banner differs from the one in the database, MemLens asks before importing anything. The Output window then says how many types IDA rejected, how many are missing and how many differ in size from the ISF. If **Show patched kernel functions** already ran on this database, Apply kernel types then applies the hook chain again (and says so in the Output window), so the ftrace_ops flags comments and the module ops' `struct ftrace_ops` type appear without opening the list a second time; on a database where the list never ran it reads no file (checked with fake IDA modules, not in IDA).
4. **MemLens: Show patched kernel functions**: opens the list, adds a comment at each entry (at a hooked entry that leads to a copied hook page, written after the hook chain below: its owner first, then the chain, also as the comment of a function that starts there, IDA's or the one MemLens makes, unless that function has a comment other than an earlier MemLens line, regular or repeatable; see [docs/OUTPUT.md](OUTPUT.md#what-you-get-real-output-from-the-demo-not-ida-screenshots)) and links the hook chain: a code cross-reference from each hooked entry to its hook page and from the page's first named call to that function, cross-references toward the page's owner (a code xref to the BPF program; data xrefs from an ftrace trampoline's `ftrace_ops` slot to the ops and from its `func` to the callback, read at the offset from the last ISF applied with Apply kernel types that has `ftrace_ops`, else 0), and a name by role for each copied hook page whose role is known (`ftrace_tramp_`, `kprobe_ftrace_tramp_`, `bpf_tramp_`, or `module_hook_` when the page's first named call is a module's function; then the hooked function's name, or the page's address when several functions share it). It renames a page once, and only while it still has its `memlens_target_<address>` label or no real name, so a name you gave it is kept; the old label stays in a comment at the page. It then makes a function (`ida_funcs.add_func`) at each address on the chain where code starts (hooked entry, hook page, handler, BPF program, owner; not an address inside another symbol) that is in an executable segment and in no function yet, so the chain should read as code before auto-analysis reaches the module area; it never deletes or redefines anything, and the Output window line counts them (`n functions created now`, plus how many were already in a function or refused by IDA); an error there is printed and the rest of the chain stays. After Apply kernel types (whose ISF gives the offset of `ftrace_ops.flags` and the `FTRACE_OPS_FL_*` values by name) it also comments each ftrace trampoline whose owner is its `ftrace_ops` (not a kprobe's), and that ops, with the ops' flags decoded and whether IPMODIFY is set, and types an ops that a module's symbol starts at as `struct ftrace_ops`, once. What it added is recorded in the database (netnode `$ memlens.hooks`), so running it again adds nothing twice and does not put back an xref or name you removed. Enter jumps to the entry; the list's Edit command, captioned **Jump to handler** in its context menu (usually Ctrl+E in IDA; not checked in IDA), jumps to the handler (on a page with no known role, whose first named call is a core-kernel helper, it says so instead), and its Insert command, captioned **Jump to owner** (usually Ins; not checked in IDA), to the owner when it is in the database. If adding the chain fails, the list is still shown and the error is in the Output window (xrefs or names added before the error are not recorded, so a second run counts them again). If the input file is missing and you pick a kernel.elf that is not the file the database was made from (by SHA-256), it asks before writing anything. On a file that is not a kernel.elf MemLens exported it shows no list and one warning that names the next step: a memory image (an ELF core dump or a LiME file, of which it reads only the first 64 bytes) points to **Export kernel from memory image** and `tools/find_isf.py`, a kernel file from disk (such as a `vmlinux`) to an export from a memory image or the demo `kernel.elf`, and anything else (also a raw memory image, which has no header to tell it by) to **Export kernel from memory image** and the demo `kernel.elf`. Not yet tried in IDA.
5. **MemLens: Add Volatility hook findings (JSON)**: pick any file in a folder of `vol -r json` outputs (the command lines are in the [README](../README.md#volatilitys-other-hook-findings-in-the-ida-list)). MemLens reads every `.json` file in that folder, in name order (a file over 16 MB is skipped), and tells each file's plugin by its field names as Volatility 2.28.2 writes them: `linux.tracing.tracepoints`, `linux.malware.keyboard_notifiers`, `linux.malware.check_idt`, `linux.malware.check_afinfo`, `linux.malware.netfilter`, and `linux.tracing.ftrace` with or without `--show-ftrace-flags`. A keyboard notifiers file must have exactly its three fields (Address, Module, Symbol), because `check_idt` and `linux.malware.tty_check` write them too, each with one more: a file with more is not read as keyboard notifiers. (Two Windows plugins write exactly the fields of two of these, `windows.ssdt` those of `check_idt` and `windows.pe_symbols` those of keyboard notifiers, so their files would be read as those; MemLens reads Linux kernels only.) It then does what Show patched kernel functions does, with a seventh column, Source, and one more row per distinct finding (exact repeats are shown once), file by file, the IDT rows last. The Output window has one line saying what each file was read as, and one warning line for each file it skipped (it cannot be opened, not JSON, the fields of another plugin, a plugin already read from an earlier file) or read in part (fields 2.28.2 does not write are ignored, rows with no address left out); if no file could be read it says so and shows no list. In a Volatility row:
   - **Address** is the callback, sign-extended (Volatility writes kernel addresses cut to 48 bits).
   - **Where** and **What** are Volatility's words: `tracepoint <name>` and the probe with its priority; `netfilter <proto> <hook>` with the handler, priority, net namespace and `Is Hooked: <value>` as Volatility wrote it; `IDT <vector>` and the handler; `afinfo <struct>.<member>` (Volatility lists a member when no kernel symbol starts at its handler); `keyboard notifier` and its `notifier_call`; `ftrace_ops <address>` with the callback, hooked symbols and flags. An absent value reads `-`, as Volatility prints it.
   - **Target** is `kernel.elf`'s name for the callback, or `<address> (not in this kernel.elf)`; **Handler** is empty; **Owner** is Volatility's Module column; **Source** is `Volatility <plugin>`.
   - Enter jumps to the callback, **Jump to owner** too when it is in `kernel.elf` (otherwise it says the owner is not in the database, or, for afinfo rows, which have no Module column, that no owner is known), and **Jump to handler** says that no handler is known.

   An ftrace row whose `ftrace_ops` is the one a MemLens row's hook page loads is not a row of its own: that MemLens row's Source becomes `MemLens; Volatility linux.tracing.ftrace: same ftrace_ops`. MemLens rows say `MemLens`. The Volatility rows are not stored in the database (run the action again to see them; Show patched kernel functions shows the list without them), and the export action does not run these plugins. Not yet tried in IDA.

## Without IDA

```
vol -p vol_plugins -s <symbols> -o <outdir> -f <image> linux.kernel2elf.Kernel2Elf [--no-percpu] [--no-modules]
python3 isf2c.py <isf.json.xz> kernel_types.h
python3 patchscan.py [--links] [--isf <isf.json.xz>] kernel.elf
```

`--links` also prints the cross-references, hook page names and owners that **Show patched kernel functions** adds in IDA. `--isf` reads the offset of `ftrace_ops.func` from that kernel's ISF (otherwise 0).

## Headless, with idalib

IDA 9.1 or newer (the IDA names MemLens uses are checked against the IDA 9.1 to 9.4 Python stubs and the 9.5 SDK's API list); set up the `idapro` module as Hex-Rays describes. After `hcli plugin install memlens` the script is in the plugin's folder, `$IDAUSR/plugins/memlens` (by default `~/.idapro/plugins/memlens` on Linux and macOS, `%APPDATA%\Hex-Rays\IDA Pro\plugins\memlens` on Windows):

```
python3 ~/.idapro/plugins/memlens/tools/memlens_headless.py kernel.elf <isf.json.xz> [--no-analysis] [--any-kernel]
```

It opens `kernel.elf` as a database, applies the types (the per-CPU copies too), comments every patched entry, links the hook chain as the menu action does, prints the same report and patch list and saves the database. It calls the plugin's own functions; like the rest of the IDA layer it has only been run against fake modules (`tests/test_headless_stub.py`), not a real idalib.
